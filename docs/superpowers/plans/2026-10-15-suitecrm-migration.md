# SuiteCRM Migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Перенести полный согласованный снимок SuiteCRM с `164.92.244.103` в установленную на `51.222.37.4` CRM, предоставив проверяемый доступ ко всем бизнес-данным.

**Architecture:** Отдельное приложение `legacy` хранит исходные бизнес-записи, связи, файлы и журнал проекций; подходящие записи дополнительно становятся штатными сущностями CRM. Импорт работает с неизменяемым снимком, сначала в отдельной PostgreSQL-базе, затем в существующей организации `CRM`; интерфейс показывает исторические данные с теми же ограничениями доступа, что и связанные карточки.

**Tech Stack:** Python 3.12, Django и SvelteKit из текущих lock-файлов, PostgreSQL 16, Redis 7, Docker Compose; изолированная MariaDB 10.11 только для чтения восстановленного SQL-снимка, PyMySQL 1.1.2 только в инструменте экспорта.

**Spec:** [Подтверждённая схема](../specs/2026-10-15-suitecrm-migration-design.md), пользователь подтвердил документ 2026-10-15. Работа ведётся в существующем linked worktree на ветке `alexkash/install`; новую рабочую копию не создавать.

## Global Constraints

- «Старая SuiteCRM продолжает работать.» Не останавливать источник, не менять его БД, SSH, DNS, почту и автоматизации.
- «Полный сброс базы не требуется.» Сохранять существующие записи и доступ владельца в `/opt/crm`.
- «Автоматическое объединение людей не выполняется.» Дубли получают согласованные отображаемые адаптации с сохранением исходных значений.
- «Данные не обрезаются, номера не угадываются.» Недопустимые для штатного поля значения доступны как исторические поля.
- «Не создаются фиктивные платежи, позиции и нулевые итоги.» Все 442 счёта обследования — исторические записи, без финансовых побочных действий.
- «Исторические письма и приглашения не отправляются повторно.» Импорт не публикует вебхуки и не повторяет конвертации.
- «Старые сессии, OAuth-токены и пароли не активируются в новой системе.» Секреты остаются только в закрытом полном снимке.
- «Неизвестная дата не заменяется текущей.» Все исходные даты и значения сохраняются; непредставимые штатно значения имеют явный результат проекции.
- «Принадлежность организации сама по себе не расширяет доступ». Новые таблицы защищены FORCE RLS, API дополнительно проверяет права на карточки.
- Числа обследования — контрольный ориентир; приёмка проводится по неизменяемому снимку T0, охватывая все его таблицы и файлы.

## Review Focus

1. ID `1`, `001`, UUID и одинаковые ID разных таблиц, а также физически одинаковые строки без PK не должны склеиваться. Проверки: задачи 1 и 3.
2. Письмо или событие с несколькими родителями, один из которых скрыт, не должно раскрывать скрытые карточки через текст, связи, поиск, счётчики или файлы. Проверки: задача 5.
3. Прерывание, повторный запуск и пользовательская правка назначения между запусками не должны создавать дубли или перезаписывать правку. Проверки: задача 7.
4. После возобновления workers исторические письма и счета не должны отправляться, менять долги или создавать платежи; нестандартная стадия не должна становиться выигрышем/проигрышем по догадке. Проверки: задачи 2, 4 и 7.
5. HTML писем, бинарные поля, кириллица, пути `../`, symlink и несовпавший хеш файла должны безопасно обрабатываться без выполнения кода и внешних запросов. Проверки: задачи 1, 5 и 6.

## Общие контракты

- `source_key = "suitecrm-coloris"`; один источник привязан к одной организации. Повторная привязка того же источника к другой организации в этой БД запрещена.
- `SnapshotManifest`: `format_version=1`, `source_key`, `captured_at_utc`, хеш SQL, хеш схемы, категории таблиц, количества total/active/deleted, поля/типы, хеши файлов и JSONL-частей. Политика таблиц обязана покрыть каждую таблицу; неизвестная таблица блокирует запись в назначение.
- `SourceRow`: `table`, `source_id`, `values`, `row_sha256`, `deleted`. Decimal хранится точной строкой, SQL NULL — JSON null, бинарные значения — объектом с типом и base64. Исходные даты хранятся строкой. Денежные значения не проходят через float.
- `stable_id(table: str, source_id: str, role: str = "native") -> UUID`: UUIDv5 с `uuid.NAMESPACE_URL` от `json.dumps([source_key, table, source_id, role], ensure_ascii=True, separators=(",", ":"))`. Исходные ID не обрезаются и не приводятся к числу.
- `ProjectionResult`: `source_record_id`, `target_model`, `target_id`, `role`, `status` (`native`, `history_only`, `conflict`), `reason`, `adaptations`, `projected_sha256`. Для каждой исходной бизнес-строки обязателен результат; тихого skip нет.
- `ImportReport`: по каждой таблице — исходное количество, историческое покрытие, штатные проекции, удалённые, закрытые служебные строки, адаптации, исходные и новые оборванные связи; отдельно — файлы, контрольные суммы, побочные действия и конфликты. `verified=true` возможно только при нулевых необъяснённых расхождениях и новых оборванных связях.
- Все fixtures синтетические. Дампы, клиентские карточки, переписка, файлы и секреты не попадают в Git, stdout тестов или публичные артефакты.
