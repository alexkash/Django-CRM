# Реализация украинских счетов и актов

Пользователь поручил создать отдельный worktree, реализовать согласованный план, затем разделить результат на четыре последовательных PR. Для каждого PR требуется разобрать замечания ботов и повторять `@codex review` до чистого результата перед началом следующего.

## Состав реализации

Одна организация CRM поддерживает несколько ФОП/ТОВ с ПДВ и без ПДВ, отдельными банками, сканами и последовательностями номеров. Компания выбирается вручную; автоматического распределения продуктов нет. Цены UA формы заданы в UAH без ПДВ, налог и итог показаны отдельно. Нулевая ставка плательщика отличается от статуса «Без ПДВ».

Явный выпуск атомарно сохраняет реквизиты, номер и два неизменяемых PDF — без сканов и со сканами подписи/печати. Выпуск не отправляет email. После выпуска доступна отдельная ручная отправка неоплаченного счёта на указанный адрес. Сканы не реализуют КЭП. Используются доверенные A4 шаблоны и включённый в пакет шрифт с лицензией; внешний доступ к файлам и сети из PDF запрещён.

Частичные акты закрывают количество и остатки net/ПДВ независимо от оплаты. Последняя часть получает точный остаток копеек. Черновики не резервируют объём, конкурентный выпуск повторно проверяет остаток под блокировкой. Отмена освобождает закрытие один раз, сохраняя номер и PDF. Копирование создаёт новый черновик без старого периода, оплат и актов.

Новые таблицы имеют FORCE RLS, а API дополнительно ограничивает организацию и видимость записей. Акт наследует доступ родительского счёта. Бинарные архивы и сканы не загружаются обычными запросами; исходные сканы доступны только администратору. Старые generic-счета не получают исполнителя автоматически.

Инструкция оператора: [billing-documents.md](../../self-hosting/billing-documents.md). API компаний: [billing-companies.md](../../api/billing-companies.md). API документов: [invoices.md](../../api/invoices.md).

## Разделение и ревью

Работа выполнена в изолированном worktree на отдельных ветках. Оригинальное рабочее дерево с изменениями SuiteCRM сохранено. `origin` — форк `alexkash/Django-CRM`, исходный проект остаётся `upstream`. Billing перенесён на актуальный `master` форка без 117 файлов сторонней миграции. Поддержка UAH и зависимости миграций адаптированы к этой базе; downgrade версии приложения не выполнялся.

Зависимые PR имеют временную базу предыдущей чистой ветки, чтобы их diff оставался отдельной частью. Финальная интеграционная цель — `master`; merge и deployment не входят в эту работу.

PR #3 не относится к этой работе. Подтверждённые замечания исправлялись с регрессиями и ответами в соответствующих ветках обсуждения. Невоспроизведённые замечания о порядке Svelte binding разобраны отдельно: браузер показывал правильные ставки/города и до изменения, затем обработчики переведены на явные выбранные значения для устранения зависимости от порядка.

Среди исправлений: сброс плательщика, наследование исправленных реквизитов, защита старых generic-счетов, сохранение пустых строк клиента, ошибки уникальности IBAN, пакетная загрузка закрытий без N+1, исчезновение акта при ожидании блокировки, длинные названия копий, сохранение контекста/полей после ошибок обычных POST, полный список из двенадцати актов, фильтр полностью закрытых счетов с сохранением бесплатных услуг, ручная отправка после выпуска и production-лимит загрузки сканов.

CodeRabbit подтвердил исправления двух своих замечаний в первом PR. Для последующих временных feature-баз его ревью отключено настройкой репозитория; это не трактуется как свежее чистое ревью. Изменений тарифов или настроек ботов не выполнялось. Один внешний сбой Codex и временные TLS-ошибки GitHub не считались чистым результатом; запросы повторялись на том же SHA.

## Проверки

- Полный backend первой части: 7814 passed, coverage 95.77%, без сбоев. Полный backend исходного финансового PR: 7910 passed, coverage 95.78%, без сбоев. После исправлений запускались затронутые регрессии: до 3117 invoice/account/case/merge тестов; отдельные generic-совместимость и PostgreSQL-проверки. Исторические четыре сбоя базы с SuiteCRM отсутствуют на выбранном `master` форка.
- Настоящий PostgreSQL под NOSUPERUSER NOBYPASSRLS: пять новых FORCE RLS политик/изоляция связанных строк, миграция вперёд/назад на пустой UA схеме, конкурентное закрытие, идемпотентный выпуск, разные номера двух счетов и отмена против выпуска. Проверены также новый список/404 и ограничения `varchar`/уникальности.
- Установленный non-editable wheel из нейтрального каталога: Django check, наличие шаблонов/CSS/font/LICENSE и настоящий рендер счёта/акта. Smoke включён в GitHub Actions.
- Веб: 103 файла / 1134 теста; Svelte без ошибок и предупреждений, production build. ESLint без ошибок, с предупреждениями существующего стиля; изменённые файлы проходят Prettier. Ruff и форматирование backend проходят.
- Реальный headless Playwright: настройки компании/банка/сканов; годовой счёт 12000+2400=14400; акт квартала 3000+600=3600; полная оплата отдельно от закрытия; месячная копия ФОП 1000 без ПДВ; клиент с пустыми реквизитами; выбор актов, закрытый и бесплатный счёт, двенадцать месячных актов; native POST ошибки с сохранением значений; пересчёт due_date; ручной запрос отправки на `.test` адрес при локальной почте и memory-broker, без реального письма.
- Desktop 1440×1000, mobile 390×844 и мобильный список осмотрены. Четыре приватных PDF через frontend валидны, clean/stamped отличаются, private/no-store подтверждены. PDF акта отрендерен и визуально проверен. Входные данные и изображения синтетические; пользовательские исходные документы не копировались.
- PNG 788 КБ воспроизвёл production 413 при стандартном лимите adapter-node; при конфигурации 3M загрузка успешна, файл больше 2 MiB получает ошибку backend. Полная Docker-сборка локально не заявляется: проверено поведение Node runtime с конфигурацией образа.
- Первые финансовые/веб-части имеют полные зелёные GitHub Actions. Для последней части схема генерируется штатным Spectacular, а новые invoice-контракты проверяются через SchemaGenerator. После замечаний к контрактам 21 целевой тест проходит: создание акта требует родителя и строки, invoice create/update описывают `custom_fields`, PUT компании и банка допускает частичные данные. Старые inference-проблемы других API не трактуются как исправленные этой механической генерацией.

Подробные журналы, временные браузерные данные и собственные QA-токены исключены из коммитов. Скриншоты и PDF проверки не содержат реальных реквизитов.

Расписания, ежемесячные work lists, уведомления, КЭП, входящие документы и налоговые накладные остаются вне согласованной первой версии. UA форма поддерживает UAH, одну ставку на счёт, без скидок и доставки. Установленный `manage.py` переопределяет settings, поэтому проверки выполнялись через `django-admin --settings=...`. Live rollback после выпуска документов заменён сохранением схемы/архивов и fix forward.
